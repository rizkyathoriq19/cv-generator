# 06 — Export and safely import independent project backups

**What to build:** A job seeker exports a portable editable snapshot and imports it into a separate CV, while malformed or incompatible files cannot overwrite projects or partially mutate the local library.

**Blocked by:** 04 — Switch between all three structures without losing content.

**Status:** implemented on `ticket-06-portable-project-backups`; code checks and the application-level run are recorded in [ticket 06 evidence](../../evidence/ticket06/README.md).

**Story coverage:** US-43, US-44, US-45, US-46, US-47, US-48, US-55.

- [x] Export the current in-memory CV as a portable snapshot of all supported sections, skill groups, dates/precision, content language, and structure; explain that the backup is unencrypted and distinct from a PDF. — `export_then_import_twice_gives_independent_copies_with_all_content` and `export_refuses_a_document_import_would_refuse` export every section, skill group, date/precision, content language, and structure, and asserts the file has no `id`/`updated_at`. UI: `Export project backup…` wrote `source-backup.json` (1,713 bytes) with keys `format, version, title, structure, content_language, cv`; the note *“…not a PDF. It is unencrypted…”* shows beside both the export and import controls (`02`, `live`). Unencrypted/not-a-PDF wording is in both interface languages.
- [x] Import always creates a new independent CV, including repeated imports of the same file and imports whose source identity matches an existing project. Verify existing projects remain unchanged. — same test imports twice, asserts distinct new ids and an unchanged source file; UI: two imports took the library from 1 to 3 files with new ids `18e8b178…0` and `18e8b17b…1`. A backup cannot carry an `id`: `unsafe_backups_are_rejected…` shows an imported `id` is rejected, so identity-matching imports cannot replace a project.
- [x] Validate supported version, schema, and bounded file size before mutating storage; reject malformed JSON, invalid data shapes, oversized files, and unsupported newer formats with accessible errors. — `unsafe_backups_are_rejected_and_leave_the_library_untouched` rejects 16 shapes (empty, non-JSON, array, truncated, no/other format marker, version 0/text, wrong type, bad structure, month 13, month without year, `id`, `path`, `updated_at`, missing `cv`) in both interface languages and byte-compares the library after each; `a_newer_backup_format_is_refused_by_name_whatever_its_shape` covers `version: 2`. UI: malformed, newer (Indonesian), and oversized files each showed a red alert and left 3 files.
- [x] Choose, document, and boundary-test explicit resource limits during implementation; the design does not supply an invented numeric product limit. — limit chosen: 2 MiB (`MAX_BACKUP_BYTES` = 2,097,152; documented in `docs/project-schema.md`). `backup_size_limit_is_exact_for_import_and_export`: a valid file of exactly 2,097,152 bytes imports, 2,097,153 is refused, export refuses a larger snapshot and writes nothing. UI: 2,097,206-byte file → `Cadangan melebihi batas 2097152 byte.`
- [x] Treat markup-looking strings as plain text and reject path traversal or imported path/identity values that attempt to escape application-controlled storage. — `markup_looking_text_imports_verbatim_into_the_library_only` imports `<script>` / `#eval(…)` / `../../escape` text verbatim and asserts exactly one `<new id>.json` appears inside the library and nothing outside; `id` and `path` fields are rejected by `deny_unknown_fields`. Rust seam only, not clicked through the UI.
- [x] Confirm destination overwrites; cancellation or write failure preserves an existing destination and does not leave a partial snapshot reported as complete. — UI: exporting over `source-backup.json` showed GTK's *“…already exists. Do you want to replace it?”*; Cancel left sha256 and mtime unchanged and no success line. `failed_or_misdirected_backup_writes_keep_the_destination`: a destination that cannot be replaced keeps its content with no temp file, a replaced file is rewritten whole, a non-`.json` destination writes nothing. `save_atomically` now also removes its temp file when the write itself fails. A mid-write failure was not forced in the UI.
- [x] Demonstrate export from one project, import twice, edit/reopen the copies independently, and render their full content through the desktop application. — evidence steps 2–5: exported the Combination/Indonesian CV, imported it twice, edited only the second copy's title, restarted; all three `cv` objects hash identically, only the second title differs, the source sha256 `8937396029eb…` is unchanged, and the import rendered Indonesian headings with all sections (`09`). Imports were rendered in the app; the PDF text equality of source vs import is asserted in the Rust test via `document_text`.
- [x] Expose controls/errors through the shared interface-language mechanism when present; later localization acceptance must include this workflow. — write-failure text now goes through `save_atomically`'s `lang` too (review fix). Strings added to `src/i18n.ts` (export/import buttons, note, file-filter name, saved status) and Rust backup messages take `interface_language`; the import error appeared in English and Indonesian (`12`, `13`, `14`). Later localization acceptance should re-check this workflow.
