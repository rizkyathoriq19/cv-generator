# 09 — Keep PDF export current and the full editor keyboard-accessible

**What to build:** A job seeker edits rapidly, previews and exports only the current CV, handles rendering errors honestly, and completes the editor/preview workflow on narrow windows or without a mouse.

**Blocked by:** 04 — Switch between all three structures without losing content.

**Status:** implemented and application-verified on Arch/Omarchy (evidence: [ticket 09](../../evidence/ticket09/README.md)); late renders, failed writes and the stale-preview export branch are proven at the code/test seam only, as listed there.

**Proposed triage:** ready-for-agent after approval. Execution still requires explicit implementation authorization.

**Story coverage:** US-30, US-31, US-32, US-33, US-34, US-35, US-36, US-37, US-48, US-52, US-53.

- [x] Refresh the generated PDF after a short editing pause and label prior content outdated while generating; associate results with the exact current content revision.
  - Evidence: `contentKey()`/`previewState()` in `src/freshness.ts`; `npm test` covers an edit, a structure switch and a content-language switch. In the app, editing `Full name` kept the old page under the banner *“This preview is not the current CV.”* and the next render replaced it (`33-outdated-banner.png`, `11-current-again.png`).
- [x] Delayed or out-of-order older results never replace a newer preview. Editing during export must not cause an old revision to be silently saved as the current CV.
  - Evidence: PDF.js canvases are built detached and inserted only while the render is the newest revision (`src/pdf.ts` + `render()`); Rust refuses an older revision (`a_late_render_result_cannot_replace_a_newer_preview`). Export reports “The CV changed after this export started…” in its own `role="status"` notice when the content key differs after the write. Out-of-order results have no public UI trigger and are proven at the seam only.
- [x] Reuse the previewed PDF artifact for export when current. If stale, generate/show the current artifact first; rendering failure preserves an older preview visibly outdated and blocks exporting it as current.
  - Evidence: `canReusePreview()` is false for stale content, an in-flight render or no preview, so `exportPdf()` renders the current revision first and returns before the save dialog if that render fails (`src/freshness.test.ts`). Reuse was clicked through: `export-current.pdf` sha256 `7f50b98058a7149cf099c05b978aa9ae750a6ac7329d1d59bec25eaa464359f5` equals the displayed `Preview SHA-256`, and `pdftotext` shows the current name (`17-exported-current.png`). A render failure keeps the previous cached bytes and the next export is refused without creating a file (`a_failed_render_keeps_the_previous_preview_and_blocks_exporting_newer_content`); the frontend's early return is by inspection, not a unit test. The stale branch was not clicked through: scrolling to the Export button outlasts the 400 ms debounce.
- [x] Confirm destination overwrites and preserve existing files on cancelled or failed PDF writes, with accessible error feedback rather than partial-success output.
  - Evidence: GTK asked *“A file named “export-current.pdf” already exists. Do you want to replace it?”* (`23-overwrite-confirm.png`); `Cancel` left mtime 1794898433, 43241 bytes and the same sha256 (`24`, `25`). A failed write keeps the destination, leaves no temp file and reports an error (`a_failed_pdf_export_keeps_the_destination_and_writes_nothing_partial`); errors render in `role="alert"`.
- [x] Exercise all three structures with long content and page-boundary headings; verify A4, intended reading order, selectable text, no clipping/loss/shrinking, and current preview/export byte identity.
  - Evidence: `long_content_keeps_a4_pages_readable_order_and_headings_with_their_content` renders one long CV in all three structures: >1 page each, every page 595.276 × 841.89 pt, every authored marker still present in the laid-out page frames, skills leading only in functional/combination, and no page ending on a bare heading. `pdftotext` extracts the headings in order and the body markers from the written PDF (e.g. `Long content marker 7-0`, `Long content marker skill 0-0`), `pdfinfo` reports 4/2/4 pages at A4. Byte identity is the exported-file sha256 above.
- [x] Wide windows show forms and preview together; narrow windows provide usable switchable tabs without a separate HTML document preview.
  - Evidence: at 1240×860 the form and PDF preview are columns (`01-wide-editor.png`); at 780×900 one pane with `Edit CV` / `PDF preview` buttons is shown (`27-narrow-tabs.png`, `28-narrow-preview.png`). The preview remains the PDF.js canvas document; no HTML preview exists.
- [x] Core library/editor/preview controls work by keyboard with labels, visible focus, accessible validation/render errors, and reorder buttons. No task requires drag-and-drop.
  - Evidence: with the `Edit CV` pane button focused, three `Tab` presses moved the visible focus outline to the project name field and the `Content structure` select and scrolled it into view (`32-keyboard-tab-traversal.png`). Inputs are wrapped in labels, reorder/remove are native buttons with accessible names, all new status output (`role="status"`) and errors (`role="alert"`) are announced, and no editor task needs drag-and-drop. Scope limit: only focus order and labelling are proven by keyboard here; reordering and the library operations rest on inspection plus the click-throughs recorded in tickets 02–08.
