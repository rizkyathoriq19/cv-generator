# 08 — Move CVs to Trash, restore, and permanently delete safely

**What to build:** A job seeker removes a CV from the active library without losing the ability to restore it, then explicitly removes its internal files when permanent deletion is intended.

**Blocked by:** 07 — Recover saved CVs and close safely after storage failures.

**Status:** implemented on `ticket-08-trash-and-restore`; application-verified on Arch/Omarchy with synthetic fixtures in an isolated library.

**Story coverage:** US-49, US-50, US-51, US-55.

- [x] Delete moves the project and its associated internal recovery state into local Trash; the active library no longer lists it and no automatic cleanup runs.
  - Evidence: `move_project_files` renames `<id>.json`, `<id>.prev.json`, and every `<id>.corrupt-*.json`; `delete_moves_the_saved_file_previous_revision_and_damaged_copy_to_trash` asserts all three land in Trash unchanged, a neighbouring id that is a prefix of the deleted id is not claimed, and a repeated listing finds them still there. App run: the seeded 1716/1717/18-byte files moved byte-identically and the library listed only the neighbour (`01-library-after-delete.png`, `02-trash-view.png`); the Trash entry was still present after a restart (`03-trash-after-restart.png`). A damaged CV (`Keep me · Rusak`) also moved with its previous revision, was restored, and still recovered on reopen (`17-library-damaged.png` … `20-damaged-restored-recovery.png`).
- [x] Restore returns the independent CV and its data to the active library without overwriting another project or silently losing content; demonstrate reopen and PDF generation after restoration.
  - Evidence: `restore_returns_the_cv_and_its_recovery_state_and_still_renders` asserts byte-identical current and previous files, an ordinary reopen, a rendered document containing the owner's name, and a following save. `a_damaged_cv_survives_trash_restore_and_recovery` rounds a damaged CV through Trash. `restore_refuses_to_overwrite_an_active_project` proves the refusal leaves both folders byte-identical. App run: Restore returned the same three files (1716/1717/18 bytes) and reopened the CV with a rendered PDF preview (`05-library-after-restore.png`, `06-restored-editor-preview.png`).
- [x] Permanent deletion requires an explicit accessible confirmation and removes the selected project plus its internal recovery copy, not unrelated projects or exported backups outside the library.
  - Evidence: `permanent_deletion_removes_only_the_selected_cv_and_leaves_exported_backups` asserts the deleted CV's files are gone, a second trashed CV and an external backup file are untouched, and the neighbour still restores; `a_failed_internal_cleanup_keeps_the_trash_row_retryable` asserts a failed internal removal leaves the listed saved file so the row stays and a retry finishes. App run: the dialog is a labelled modal with the CV name, the removed recovery copy, and the statement that permanent deletion is not secure erasure; `Cancel` is focused, `Tab` cycles only between `Cancel` and `Delete permanently` (also after clicking the dialog body, which blurs the buttons), and `Escape` cancels from either state. After confirmation only a 0-byte `<id>.deleted.json` marker remained, the other CV was unchanged, and the 541-byte external backup kept sha256 `ce5215a6…7d8b` (`07-permanent-confirm-dialog.png`, `08-cancelled-permanent-delete.png`, `09-permanent-deleted.png`, `21-confirm-dialog-not-secure-erasure.png` … `27-dialog-body-click-escape.png`).
- [x] Flush or explicitly resolve pending edits before a move/delete action; late autosave completion must not resurrect a permanently deleted project.
  - Evidence: the delete handler awaits `flush()` and a failed flush keeps the CV in the library; leaving the editor already awaits the pending write (ticket 07). Rust refuses a save for an id in Trash, and a permanent deletion leaves a marker so a save already in flight is refused: `a_late_save_cannot_resurrect_a_deleted_or_permanently_deleted_cv` covers both states and asserts neither recreates a file. The exact race has no public-UI path, so it is proven at the Rust seam only.
- [x] Explain that Trash and recovery data are unencrypted and that deletion is not secure erasure. Keep all controls/notices within the shared interface-language mechanism.
  - Evidence: `trashNote`, `deleteTitle`, and `deleteBody` live in the shared `STRINGS` table; Rust refusals pick the interface language. `trash_controls_and_refusals_follow_the_interface_language` asserts English and Indonesian messages for delete, restore, permanent delete, and the save guard. App run: the English note and dialog (`02-trash-view.png`, `07-permanent-confirm-dialog.png`) and the Indonesian equivalents (`11-indonesian-trash-empty.png`, `14-indonesian-confirm-dialog.png`, `21-confirm-dialog-not-secure-erasure.png`: *“… penghapusan permanen bukan penghapusan aman …”*) were shown without switching the CV content language.
- [x] Exercise delete/restore across restart, cancelled permanent deletion, successful internal cleanup, and untouched external backup fixtures through public application behavior.
  - Evidence: the app run stopped and restarted between delete and restore (`03-trash-after-restart.png`), cancelled permanent deletion with `Escape` and `Batal` while the files stayed byte-identical (`08-cancelled-permanent-delete.png`, Indonesian `14-indonesian-confirm-dialog.png`), confirmed cleanup (`09-permanent-deleted.png`), and compared the external backup's size and sha256 before and after. Full commands and observed values: [evidence](evidence/ticket08/README.md).

**Seam-only coverage:** restore identity collisions, the late-save guards, and an induced mid-cleanup removal failure are not reachable through the public UI (ids are generated and never reused; the editor is closed before deletion; the app run does not fabricate filesystem errors), so they are asserted at the Rust seam. Native Windows/Ubuntu runs and a frontend test harness remain out of scope (tickets 10/11).
